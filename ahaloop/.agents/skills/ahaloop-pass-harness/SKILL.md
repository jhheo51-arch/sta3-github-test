# 아하루프 패스 하네스

## 목적

`혜택을 찾는 서비스`가 아니라 `혜택을 받기까지 사용자가 해야 할 일을 줄이는 서비스`라는 원칙을 코드와 측정으로 지킨다. 기능 구현, 합성 하네스 통과, 실제 고객 성과를 구분한다.

## 제품 불변 조건

- 신규 사용자는 `거주지 → 만 나이 → 생활 상태` 세 번의 선택 안에 첫 혜택을 본다.
- 첫 혜택 전에는 소득·재산·서류·연락처를 요구하지 않는다.
- 첫 혜택 이후에는 한 화면에서 질문 또는 결정 하나만 제시한다.
- 이미 확인한 조건은 재사용하고, 법·기관상 재확인이 필요할 때만 이유와 함께 다시 묻는다.
- 본인인증, 약관 동의, 기관 제출과 최종 신청은 사용자 승인 없이 자동화하지 않는다.
- 신청함에서도 현재 단계의 다음 행동 하나를 먼저 보여 주고, 전체 준비 순서는 보조 정보로 둔다.

## 구현 기준

- 핵심 게이트는 `lib/ahaloop-pass.ts`의 `passProgress`를 재사용한다.
- 표시할 다음 질문은 `activeBenefitQuestion`을 재사용해 한 개로 제한한다.
- 패스 측정은 `/api/pass-event`의 제한된 이벤트만 사용한다. 원문 답변이나 민감정보를 이벤트 속성에 넣지 않는다.
- 제품 지표는 `pass_session_started`, `pass_first_benefit_viewed`, 선택 수, 경과시간, 다음 질문 확인을 사용한다. 준비·신청·수령 이벤트와 연결하기 전에는 전환 인과를 주장하지 않는다.
- 새 프로필 필드를 추가하면 선택 UI, API 검증, 판정 규칙, 데이터 보관 이유와 삭제 기준을 함께 확인한다.

## 반복 검증

패스 화면·프로필 재사용·질문 규칙·성과 측정을 바꾼 뒤 프로젝트 루트에서 `npm run harness:pass`를 실행한다. 이 명령은 패스 불변 조건, 기존 판정 회귀, 린트와 빌드를 차례로 확인한다.

실제 브라우저에서는 신규 빈 프로필과 기존 조건 보유 프로필을 각각 확인한다. 모바일에서 가로 넘침, 키보드 초점, 44px 이상의 선택 영역, 상태 안내를 점검한다.

첫 5명 관찰은 `docs/AHALOOP_Pilot_Operations_v1.0.md`의 익명 슬롯에 기록한다. 선택 수·시간·준비 시작·중단 지점은 실제 관찰 값만 저장하고 빈 슬롯이나 계획을 성과로 집계하지 않는다.

## 지속 자동화

- `.github/workflows/ahaloop-harness.yml`은 `ahaloop/**` 변경이 있는 PR과 브랜치 반영에서 `npm run harness:pass`를 실행한다.
- `main`은 `AHALOOP harness` 상태 검사를 필수로 요구한다. 자동검사가 실패한 변경을 우회해 병합하지 않는다.
- 예외적으로 `main` 반영 뒤 하네스가 실패하면 원인 커밋을 직접 덮어쓰지 않고 되돌림 PR을 만든다. 되돌림 PR도 같은 하네스를 통과한 뒤에만 자동 병합한다.
- `.github/workflows/ahaloop-operations-monitor.yml`은 비공개 Sites의 로그인 장벽을 우회하지 않고 30분마다 사이트 접속 가능 여부만 확인한다. 실패 시 GitHub 이슈를 열고 정상화 후 닫는다. 경고 본문에 고객 정보·원문 내용·인증값을 넣지 않는다.
- 실제 운영 데이터는 운영자 전용 검증실을 열면 즉시 점검하고, 화면을 열어 둔 동안 30분마다 다시 점검한다. 브라우저가 닫힌 시간을 백그라운드 데이터 감시 완료로 기록하지 않는다.
- `/api/operations-health`는 출처 검수 지연·수집 실패, 발송 실패·확인 불가·장시간 처리 중, 패스 이벤트 이상, 불완전 수령 기록, 기한 초과 후속 작업만 감시한다. 실제 원문 재수집이나 메시지 재발송은 자동 실행하지 않는다.
- 운영 경고는 실제 데이터에서 계산하며 데이터 없음과 정상 0건을 구분한다. GitHub 워크플로 성공을 고객 성과로 해석하지 않는다.

## 완료 기록

하네스 통과는 구현 검증으로만 기록한다. 실제 첫 혜택 도달률, 소요시간, 준비 시작률은 실제 세션이 생긴 뒤 별도로 기록하고, 0건을 0% 성과로 표시하지 않는다.
