# 아하루프 제품 개발

## 기준 자료

작업을 시작할 때 최상위 `작업일지.md`의 마지막 기록을 읽는다. 현재 제품 요구를 해석하거나 범위를 바꾸는 작업이면 `docs/AHALOOP_Benefit_Recovery_PRD_v1.0.md`를 우선 기준으로 삼고, 기존 뉴스 기반 이력은 `docs/InsightFlow_CRM_PRD_v5.0.docx`를 참고한다. PRD와 충돌하는 요청은 사용자의 최신 명시적 요청을 우선하고, 바뀐 결정을 작업일지에 남긴다.

외부 브랜드명, 마스코트, 색상과 대외 표기를 다루는 작업은 `docs/AHALOOP_Brand_PRD_v1.0.md`를 함께 기준으로 삼는다. 신규 사용자 노출에는 `아하루프` 또는 `AHALOOP`를 사용하고, `InsightFlow CRM`은 기존 자료와 코드의 레거시 내부 코드명으로만 보존한다. 기능·데이터·운영 규칙은 브랜드 변경만을 이유로 바꾸지 않는다.

이 프로젝트의 주 지원 직무는 BA다. 컨설턴트식 문제 정의·대안 비교·권고를 차별화 역량으로 사용하고, PM은 실제 사용자 성과와 협업 근거가 생긴 뒤의 확장 경로로 둔다. 구현할 때 요구·예외·수용 기준, 현재/개선 프로세스, 데이터 근거와 권고가 연결되는지 확인하고 `docs/AHALOOP_Career_Portfolio_Evidence_v1.0.md`를 갱신한다. 실제 데이터와 데모 설계를 구분하며 미검증 결과를 성과로 쓰지 않는다.

## 제품 불변 조건

- 현재 핵심 여정은 `혜택 발견 → 조건 확인 → 서류 준비 → 신청 → 승인 → 수령`이다. 뉴스·인사이트 추천 여정은 레거시 실험으로 보존하되 신규 기본 화면으로 확장하지 않는다.
- 제품 약속은 혜택 정보량이 아니라 사용자가 해야 할 선택·입력·판단을 줄이는 것이다. 신규 사용자는 지역·만 나이·생활 상태 세 번 안에 첫 혜택을 보고, 이후 한 화면에서 질문 또는 결정 하나만 받는다.
- 아하루프 패스와 접근 부담 측정을 바꿀 때 `.agents/skills/ahaloop-pass-harness/SKILL.md`를 함께 사용한다.
- 목록 수보다 회수 가능성이 높은 가치와 다음 행동을 먼저 보여 준다. 월간, 1회성, 비현금 가치를 구분하며 계산 가정과 공식 원문 확인일을 표시한다.
- 자격 판정은 맞는 조건, 맞지 않는 조건, 모르는 조건을 분리한다. 정보가 없으면 질문하고 선정·지급을 보장하지 않는다.
- 혜택 수집·판정·갱신에는 `.agents/skills/ahaloop-benefit-recovery/SKILL.md`를 함께 사용한다.
- 2026-09-18 최신 수집 결정은 공식 공개 공고 우선이며 로그인·인증키 발급은 보류다. 과거 API 우선 로드맵을 현재 필수 절차로 안내하지 않는다. 수집 실패 대응·청년몽땅정보통 연결에는 혜택 스킬의 `references/public-notice-operations.md`를 읽는다. 문서화와 실제 연결·예약 실행·배포 완료를 구분한다.
- 혜택용 `브리프`는 `현재 생활 조건에서 회수 가능성이 있는 혜택의 가치, 판정 근거와 다음 행동만 이어 붙인 개인화 준비 묶음`으로 정의한다.
- 고객군은 전국 전 생애주기다. 2026-09-18 최신 요청으로 기본 조건 입력은 선택형이다. 지역·만 나이, 생활·가구·주거, 복수 도움 선택을 요약·개별 해제·초기화와 연결한다. 기본 고객 화면에 자연어 작성을 요구하지 않으며 기존 해석 API는 실험용으로 보존한다. 저장 전 선택 초안과 저장된 혜택 결과를 구분한다.
- 제품 범위와 파일럿 표본을 혼합하지 않는다. 2026-09-26 첫 외부 검증은 서울 거주 만 19~34세 직장인·구직자 중 최근 6개월 내 정책·지원금 탐색 경험이 있는 5명으로 시작한다. 마감이 있는 현금성 혜택의 3회 내 첫 혜택 도달, 준비 시작, 중단 지점을 관찰하며 결과를 전국·전 생애주기 성과로 일반화하지 않는다.
- 파일럿 운영은 `docs/AHALOOP_Pilot_Operations_v1.0.md`를 따른다. `P01~P05` 익명 코드와 동의 상태, 선택 수·시간, 준비 시작, 중단 지점만 저장하며 실명·연락처·민감서류를 받지 않는다. 계획·빈 슬롯을 실제 참여로 계산하지 않는다.
- selectProfileField/resetProfileConditions를 공통으로 사용한다. 미선택과 빈 숫자는 confirmedFields에서 제거하고 명시한 0/false는 유지한다. 조건 초기화는 이름·알림 동의를 바꾸지 않는다.
- 혜택 범위와 신속성을 함께 관리한다. 출처 연결 상태와 발견→검수→알림 시간을 분리하고, 인증키나 실제 예약 실행이 없는 수집원을 자동 운영 중으로 표현하지 않는다.
- 혜택 알림은 새 발견, 마감 임박, 진행 이어가기, 수령 확인으로 구분한다. 받은 이유·가치 유형·마감·공식 확인일과 다음 행동 하나를 기본 단위로 삼고, 중복·완료 단계 재촉·광고 혼합을 막는다.
- 경쟁 서비스 분석은 공개 화면과 공식 자료의 확인 가능한 사실, 그로부터 얻은 제품 가설, 아하루프 적용 결정을 분리한다. 비공개 개인화나 성과를 추정해 사실처럼 기록하지 않는다.

- 아래 뉴스·Action Pulse 규칙은 레거시 뉴스 화면을 유지보수할 때만 적용한다.
- 관심 분야와 역할은 각각 최대 2개다. 선택하지 않은 정보 유형과 동의하지 않은 채널은 발송 대상에서 제외한다.
- 주간 발송은 검수된 카드 3~5개로 구성한다. 카드에는 제목, 요약, 개인화 이유, 출처, 게시·검수 시점과 행동이 있어야 한다.
- `브리프`는 `한 주의 정보 흐름에서 나에게 필요한 맥락과 다음 행동만 이어 붙인 개인화 묶음`이라는 아하루프 고유 정의를 유지한다.
- `오호, 더 보고 싶어요`는 관련 뉴스 1개를 즉시 펼치고 이어서 명확히 표시된 유료 광고 영역을 노출한다. 광고 뒤 `더 많은 흐름으로 이어가고 싶나요?` CTA는 `paid_loop_interest` 이벤트로 저장하며 운영 후속 Task는 만들지 않는다.
- `담당자에게 검토 요청`은 문제 설명 10~1000자를 받아 요청 내용과 함께 48시간 내 첫 응답 Task로 저장하고, `아하! 이번 주 해볼래요`는 3일 뒤 한 번의 확인으로 이어진다.
- 평가 제출은 다음 주 관련 뉴스 1개 추가로 이어지며, 평가 보상에는 광고를 붙이지 않는다.
- `이번 주 쉬기`는 해당 회차만 멈춘다. 재개 안내 동의가 있을 때만 7일 뒤 한 번 안내하며, 수신 종료는 모든 홍보성 발송을 즉시 멈춘다.
- 자동화 결과는 운영자가 출처, 마감일과 문구를 검수한 뒤 발송할 수 있게 한다.

## 고객 채널 경험

알림 설정은 희망 채널·동의 저장과 실제 연결을 분리한다. 실제 발송 작업에는 `docs/AHALOOP_Notification_Pilot_v1.0.md`를 읽는다. 현재 솔라피 운영자 본인 번호 테스트만 구현하며 계정·비밀 설정 미연결 상태다. 일반 고객 인증·자동발송 완료로 표현하지 않는다. 요청 접수/실패/결과 불명을 구분하고 불명 요청을 자동 재발송하지 않는다. 검증은 `node tests/notification-check.mjs` 모의 응답 및 로컬 API 검사로 수행하고 실문자 테스트는 별도 동의 후에만 한다.

금액 화면은 `benefitValueState` 공통 분류를 사용한다. 월·연·1회 합계는 양수인 계산값만 해당 단위로 표시하고 정보 부족·계산 기능 미지원·비현금 후보·대상 제외와 구분한다. 실제 입력에 따른 계산액 0과 미확인 값을 혼합하지 않는다.

카카오톡과 문자 발송을 다룰 때는 운영자 발송안, 고객 수신 미리보기, 상세 브리프 도착 화면을 한 흐름으로 확인한다. 흰 족제비 마스코트의 작업용 애칭은 `아루`이며 `public/brand/ahaloop-mascot-profile.png`를 대표 프로필로 유지한다. 애칭은 사용자 노출에서 제품명보다 앞세우지 않는다.

알림 발신자명은 `아하루프 혜택알림`을 우선 검증한다. `아하루프`만 처음 본 고객이 서비스 범주를 이해하기 어렵다는 브랜드 약점을 설명 문구 `놓친 혜택을 받을 때까지`로 보완한다.

`Action Pulse` 기능명은 유지한다. 실행·추가 추천·도움·쉬기 문구는 `아하`의 발견이 작은 행동과 다음 추천으로 이어지는 느낌을 살리되, 처음 보는 고객도 각 행동의 결과를 바로 이해할 수 있어야 한다.

레거시 뉴스 콘텐츠를 실제로 수집하거나 갱신할 때만 `.agents/skills/ahaloop-content-collector/SKILL.md`를 함께 사용한다. 혜택에는 `ahaloop-benefit-recovery`를 사용한다.

카카오톡 채널 이름·검색용 아이디·소개글은 개설 전 초안으로 구분한다. 특히 검색용 아이디는 실제 채널에서 확정된 값으로 교체하고, 친구추가 링크와 QR 코드는 관리자센터의 홍보 메뉴에서 발급된 자산만 고객 홍보물에 사용한다. 광고성 홍보 문구는 동의한 고객에게만 보내며 `(광고)` 표시와 수신거부 방법을 포함한다.

## 구현 방식

2026-09-18 포트폴리오 고도화 이후 요구 추적·지표·검증 범위는 `docs/AHALOOP_Portfolio_Upgrade_v2.0.md`를 읽고 따른다. 검증실의 요구·판정, 수집·검수, CRM 실험, 사용자·결정, 사업 판단 화면을 같은 데이터와 연결한다. 단순 계획표를 실행된 실험으로 표현하지 않는다.

계정 ID는 서버 인증에서만 얻는다. 실제 고객 데이터에 공통 demo-user나 클라이언트 userId를 쓰지 않는다. `AHALOOP_OPERATOR_USER_IDS` 서버 설정으로 고객과 운영자를 분리하고 검증실·파일럿·실발송 테스트 API에서 역할을 다시 검사한다. 개인 검증실의 검수 승인은 공개 규칙 배포 권한이 아니다.

외부 파일럿 주소를 열 때는 페이지 진입에서 ChatGPT 로그인을 요구하고 API에서도 다시 로그인 상태를 검사한다. 고객 계정에는 혜택 브리프·신청함·내 조건·수신 미리보기만 보이며, 출처·성과·검증실과 실제 발송 테스트는 운영자 역할로 차단한다. 사이트 공개 범위를 고객 데이터 공개나 익명 사용 허용으로 해석하지 않는다.

보관과 삭제는 `docs/AHALOOP_Data_Retention_v1.0.md`를 따른다. 접속 시 만료된 발송 시도·활동·후속 기록을 계정 범위에서 정리하고, 사용자의 확인 문구 뒤 프로필·신청함·동의·이벤트·운영 기록을 한 번에 삭제한다. 공유 혜택 목록과 로그인 계정 자체는 삭제하지 않는다.

정확한 만 나이가 없으면 출생연도에서 단정하지 않는다. `confirmedFields`에 없는 0/false 값은 미확인이다. 상태 전이는 조건부 쓰기와 이벤트를 같은 DB 작업으로 처리한다. 준비 시작 주차는 감시 생성일이 아니라 첫 준비 시작 이벤트로 정의한다.

반복 검증: `node tests/portfolio-check.mjs`는 합성 50문장·추가 반례·금액/마감 규칙, `node tests/local-api-check.mjs`는 localhost 전용 저장·단계·동의 검사다. 후자는 합성 기록을 로컬 저장소에 만들므로 실사용 성과와 혼합하지 않는다.

패스 화면·프로필 재사용·질문 순서·접근 부담 KPI를 바꾸면 `npm run harness:pass`를 실행한다. 하네스 통과는 구현 검증이며 실제 고객의 도달률·시간·전환 성과가 아니다.

사용자 화면과 운영 화면이 같은 이벤트와 데이터에 연결되도록 만든다. 화면 전용 가짜 상태를 따로 쌓지 말고, 실제 저장·반응·평가·Task 생성 흐름을 사용한다. 예시 콘텐츠는 사실처럼 오인되지 않는 데모 데이터로 유지한다.

신청함은 현재 단계에서 필요한 행동 하나를 먼저 보여 준다. 전체 준비 순서는 접을 수 있는 보조 정보로 제공하고, 공식 원문을 항상 연결한다. 외부 신청·승인·수령은 자기보고 확인 없이는 상태를 넘기지 않는다.

데이터 구조를 바꿀 때는 관련 스키마, 서버 처리, UI와 마이그레이션을 함께 갱신한다. 이미 적용된 마이그레이션은 수정하지 않고 새 변경을 추가한다. 개인정보와 채널 동의는 필요한 범위만 저장하며 비밀값이나 실제 고객 자료를 예시에 넣지 않는다.

## 완료 확인

의미 있는 변경 뒤에 빌드를 실행하고 다음을 확인한다.

- 관심 분야·역할의 최대 2개 제한과 정보 유형 선택
- 카드 저장, 실행, 추가 추천, 도움 요청, 쉬기 이벤트
- 평가 제출과 다음 회차 반영 정보
- 후속 Task의 기한과 상태, 채널 동의·철회
- 핵심 화면의 모바일·데스크톱 사용성
- 카카오톡·문자 수신 미리보기, 마스코트 프로필, 상세 인사이트 연결
- 혜택 조건 저장, 준비 시작, 단계 이동, 변화 감시와 금액 구분

완료한 내용, 실제 검증 결과, 남은 제한과 다음 할 일을 최상위 `작업일지.md`에 덧붙인다. 반복해서 발견한 제품 규칙이나 작업 방식은 이 스킬과 `AGENTS.md`에도 반영한다.
