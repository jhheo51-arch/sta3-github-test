# 아하루프 혜택 회수

## 기준

`docs/AHALOOP_Benefit_Recovery_PRD_v1.0.md`와 최상위 `작업일지.md`의 최신 결정을 먼저 확인한다. 새 요구가 기존 PRD와 충돌하면 사용자의 최신 명시 요청을 우선하고 문서에 결정 이유를 남긴다.

## 수집과 검수

- 2026-09-18 사용자 결정: 공식 공개 공고 수집을 우선하고 API 로그인·활용 신청·인증키 발급은 보류한다. 공개 공고 연결·장애 대응·수집 확대에는 [public-notice-operations.md](references/public-notice-operations.md)를 먼저 읽는다. 이 참조는 운영 설계이며 실행 완료 증거가 아니다.

- 현재 실행 가능한 수집은 검증실의 등록 공식 URL 단건 조회다. 전체 본문 해시와 앞 5,000자 발췌를 저장하며 메뉴·날짜 변경도 감지할 수 있다. `pending/changed/unchanged/failed/approved/rejected`를 구분하고 실패 뒤 비교 기준은 마지막 성공 원문을 유지한다.
- 출처별 자동 접근 허용과 실제 예약 실행이 확인되기 전까지 위 기능은 운영자 수동 변경 감시다. 수동 실행을 자동 수집으로 표현하지 않으며, 자동화로 승격할 때 마지막 성공 시각·실패 알림·호출 주기와 검수 대기열을 함께 연결한다.
- 개인 검수 승인만으로 공개 자격 규칙을 변경하거나 알림을 보내지 않는다. 공식 API 인증키·기관 약관·호출 한도와 예약 실행을 연결하기 전에는 수동 실행이라고 표시한다. 인증키를 채팅·저장소·작업일지에 넣지 않는다.

- 정부·지자체·공공기관·혜택 제공자의 공식 원문을 우선한다. 검색 결과나 재배포 요약만으로 자격을 판정하지 않는다.
- 혜택별로 제공기관, 지역, 나이, 소득, 고용·주거·가구 조건, 신청 기간, 가치 유형, 계산식, 공식 URL, 원문 확인일과 검수 상태를 정규화한다.
- 공고 ID와 공식 URL을 중복키로 사용하고, 조건이나 기간이 바뀌면 기존 판정을 덮지 말고 계산식·원문 버전을 추적한다.
- 자동 수집은 `수집 → 정규화 → 중복 제거 → 변경 감지 → 검수 대기`까지만 수행한다. 운영 승인 없이 고객 판정이나 발송으로 넘기지 않는다.
- 현재 출처는 공식 공개 페이지 중심으로 검증하고, 보조금24·복지로·온통청년 API는 향후 확장 후보로 보존한다. 청년몽땅정보통은 정책 정보와 청년지원정보를 별도 후보로 관리한다. 출처 선택·연결 상태·주기는 [source-registry.md](references/source-registry.md)를 따른다.
- `자동 수집`, `변경 감시 준비`, `수동 검수`, `인증키 필요`를 서로 다른 상태로 저장한다. 실제 실행과 마지막 성공 시각이 없는 출처를 자동 수집 중이라고 표시하지 않는다.
- 발견 지연, 검수 지연, 대상자 알림 지연을 별도 이벤트와 지표로 남긴다. 마감 7일 이내, 조건·금액 변경, 안전·돌봄 위험은 P0로 승격한다.

## 판정과 금액

- `lib/benefit-rules.ts`의 공통 판정을 조회와 신청 저장에서 함께 사용한다. 기준은 사용자 확인 필드이며, K-패스 카드 등록·월 이용 횟수·대상 교통비가 없으면 금액을 합산하지 않는다. 현재 산식은 단순 계산 예시이고 기관 정산액이 아니다.
- 예상액과 자기보고 수령액·수령일·기록 방식을 분리한다. 신청 기간이 끝나더라도 이미 제출·승인된 건의 수령 사실 입력은 허용한다. 동일 단계의 경쟁 요청으로 상태가 되돌아가거나 이력이 중복되지 않게 조건부 저장한다.
- 공식 마감 시각이 있으면 시간대를 함께 비교한다. 날짜만 있으면 한국 날짜 기준으로 다음 날 종료 처리하고 당일에는 마감 시각 기관 확인을 표시한다. 18시·23:59 등 미확인 시각을 만들거나 당일 접수 가능을 보장하지 않는다. 자유문자·예산 소진 기한은 별도 미확인 상태다. 상세 수용 기준과 지표는 `docs/AHALOOP_Portfolio_Upgrade_v2.0.md`를 따른다.

- 결과를 `가능성 높음`, `정보 필요`, `현재 대상 아님`, `다음 회차 감시`로 구분한다.
- 판정 결과에는 맞는 조건, 맞지 않는 조건, 아직 모르는 조건을 분리한다. 모르는 조건을 임의로 통과시키지 않는다.
- 월간·연간·1회성·비현금 가치를 섞어 하나의 월 금액처럼 표시하지 않는다. 가정과 산식을 함께 보여 주고 현재 자격이 없거나 마감된 혜택은 합계에서 제외한다.
- 선정·지급을 보장하지 않는다. 공식 원문과 확인일을 고객이 항상 확인할 수 있게 한다.

## 선택형 조건 확인과 기존 자연어 해석

- 2026-09-18 이후 고객 기본 입력은 선택형이다. 지역·나이·생활 / 가구·주거 / 추가 조건 / 알림 설정을 분리하고 선택 요약에서 개별 해제할 수 있게 한다. 문장 해석은 기본 화면에서 요구하지 않는다.
- 선택 초안은 명시적 저장 전 혜택 결과에 섞지 않는다. 미선택은 unknown이며 빈 숫자를 0원으로 확정하지 않는다. 예/아니요/미선택을 구분하고 알림 동의는 별도 선택으로 유지한다.
- 아래 자연어 규칙은 보존된 해석 API와 평가셋을 유지보수할 때 적용한다.

- 고객군은 전국 전 생애주기다. 지역과 만 나이 다음에 학생·재직·구직·가사돌봄·은퇴 등 생활단계, 1인·부부·자녀·한부모·조손 등 가구형태, 돌봄·이동·장애·안전 필요를 확인한다.
- 사용자의 원문 진술과 추출한 값, 해당 근거 표현, 신뢰도, 아직 모르는 값을 분리한다. 해석한 결과를 사용자가 확인·수정한 뒤 저장한다.
- 모르는 값을 과거 프로필이나 기본값으로 조용히 확정하지 않는다. 예상 가치나 마감 우선순위에 가장 크게 영향을 주는 후속 질문을 한 번에 하나씩 묻는다.
- 주거, 소득, 교통비와 이사·퇴사·졸업 등 생활 변화 맥락은 관련 혜택을 좁히는 데 사용하되 필요 이상으로 수집하지 않는다.

## 회수 흐름

혜택별 상태를 `발견 → 조건 확인 → 서류 준비 → 신청 → 승인 → 수령`으로 관리한다. 자격 변화 감시는 별도 상태로 둔다. 고객이 외부 제출과 민감정보 제공을 승인하는 지점을 명확히 분리한다.

신청함에는 단계별 `지금 할 일 하나`를 우선 표시하고 공식 원문과 전체 준비 순서를 보조 정보로 제공한다. 다음 단계 저장은 현재 단계와 사용자의 외부 진행 자기보고를 함께 검증한다. 수령액·수령일은 승인 단계에서만 받는다.

고객에게는 첫 혜택 전 지역·만 나이·생활 상태만 차례로 묻고, 세 번째 선택에서 첫 후보를 연다. 이후에는 한 화면에 다음 질문 또는 결정 하나만 제시하고 이미 확인한 조건을 재사용한다. 패스 흐름과 접근 부담 측정은 `.agents/skills/ahaloop-pass-harness/SKILL.md`를 따른다. 수신 메시지는 목록 개수보다 예상 가치, 마감과 다음 질문 하나를 우선한다. `브리프`는 혜택의 가치, 판정 근거와 다음 행동을 이어 붙인 개인화 준비 묶음이라는 정의를 유지한다.

## 알림 설계

- `새 혜택 발견`, `마감 임박`, `진행 이어가기`, `수령 확인` 중 실제 고객 상태와 맞는 유형만 선택한다.
- 알림에는 받은 이유, 월간·1회성·비현금 중 가치 유형, 마감, 원문 확인일, 질문 또는 CTA 하나를 포함한다.
- 마감 7일·3일·1일 전이나 조건 변경 때 재판정하되 같은 혜택과 사유를 중복 발송하지 않는다. 준비·신청·수령 완료 상태를 반영해 이미 끝낸 행동을 재촉하지 않는다.
- 공개된 경쟁 서비스의 일정·금액·짧은 CTA 패턴은 참고할 수 있지만 비공개 알림을 추정하거나 문구를 복제하지 않는다. 광고·제휴는 판정과 시각적으로 분리한다.
- `notification_open`, `notification_action`, 단계 이동과 수령 확인을 연결해 클릭률보다 수령 완료 기여를 우선 평가한다.
- 위 notification 이벤트는 실제 제공업체 발송 ID를 검증할 수 있을 때만 사용한다. 현재 수신 미리보기는 `preview_open/preview_action`으로 저장하고 실캠페인 효과에서 제외한다.

## 완료 확인

- 공식 원문 링크와 확인일, 자격 조건, 금액 계산 근거를 검증한다.
- 화면, API, 스키마와 새 마이그레이션이 같은 상태 모델을 사용하는지 확인한다.
- 조건 저장, 준비 시작, 단계 이동, 감시, 빈 상태와 오류 상태를 실제로 시험한다.
- 데스크톱·모바일과 카카오톡·문자 수신 화면에서 오해할 금액 표현이 없는지 확인한다.
- 빌드와 린트를 실행하고 결과·제약·다음 결정을 `작업일지.md`에 기록한다.
- 파일럿 변경이면 `P01~P05`가 익명·동의 기반으로 저장되는지, 0건을 0% 성과로 보이지 않는지, 고객이 운영자 API에 접근할 수 없는지 확인한다.
