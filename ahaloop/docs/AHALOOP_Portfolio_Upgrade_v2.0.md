# 아하루프 BA 중심 · 컨설턴트형 문제 해결 포트폴리오 v2.0

작성일: 2026-09-18. 범위: 전국·전 생애주기 혜택 발견부터 수령·이용까지. 기존 문서는 이력으로 보존하며 아래 검증 수준과 최신 결정을 우선한다.

2026-09-26 결정: 지원 직무는 BA를 중심으로 좁히고, 컨설턴트식 문제 정의·대안 비교·권고를 차별화 역량으로 사용한다. CRM은 분석 수단, PM은 실제 사용자 성과와 협업 근거가 생긴 뒤의 확장 경로로 둔다.

## 1. 이 프로젝트가 증명할 것

“AI로 혜택 사이트를 만들었다”보다 “잘못된 확정·섞인 지표를 찾아 요구·판정·고객 행동·운영 의사결정을 연결했다”를 사례의 중심에 둔다.

| 직무 | 증거 | 현재 구현·산출물 | 외부 검증이 필요한 부분 |
|---|---|---|---|
| BA: 업무 문제와 요구를 구조화 | 현재/개선 흐름, 요구 추적, 예외 기준 | 검증실 요구·판정, 규칙 버전, 50문장 평가 | 실제 기관 담당자와 자격 규칙 검토 |
| CRM: 고객 행동을 다음 접점에 연결 | 계정 분리, 동의, 단계 이력, 메시지 그룹 | 사용자 단위 단계, 신청 건별 주차, 문구 고정 배정, 발송 전 조건 검사 | 제공업체 발송·도달·클릭, 전체 고객 관리자 권한 |
| Consultant: 대안을 비교하고 권고 | API/개발/제휴 비용과 위험 | 비용 민감도 계산기, 공식 출처, 90일 계획 | 실제 운영시간·제휴 견적·지불의사 |
| PM: 문제·가설·우선순위·학습 | 사용자 테스트와 결정 기록 | 10명 테스트 키트, 근거 기록 저장·내보내기 | 실제 참여자 모집, 관찰과 회고 |

기능 구현은 고객 성과가 아니다. 합성 문장 테스트 통과는 실제 자연어 정확도가 아니다. 로컬 테스트의 수령 금액은 실제 고객 실적이 아니다.

## 2. 문제 정의와 흐름

기존 PRD의 “기존 정책 검색과 알림은 발견 단계에서 끝난다”는 경쟁 서비스 전체에 대해 검증되지 않은 일반화다. 최신 가설은 **탐색 이후 조건 확인·신청 준비에서 이탈하는 사람이 있으며, 근거와 다음 행동을 연결하면 이를 줄일 수 있다**이다.

현재 흐름: 흩어진 공고 검색 → 여러 필터·로그인·반복 입력 → 스스로 자격 해석 → 서류 확인 → 외부 신청 → 진행 상황 별도 관리.

개선 흐름: 지역·만 나이·생활 상태 3회 선택 → 첫 혜택 → 한 화면 한 질문 → 확인한 조건 재사용 → 일치/불일치/미확인 → 단위별 계산 예시 → 준비 → 기관에서 직접 제출·승인 → 자기보고 수령/이용 → 다음 조건 변화 확인.

운영자 흐름: 공식 원문 조회 → 성공/실패와 시각 기록 → 전체 본문 해시 비교 → 이전/현재 발췌 대조 → 검수 의견 → 승인/반려 기록. 현재 검수는 계정별 파일럿 기록이다. 승인만으로 공개 판정 규칙·고객 발송이 변경되지 않는다.

## 4. 예외 수용 기준

1. AC-01: 신규 프로필에는 서울/27세/교통비를 자동 입력하지 않는다. 모르는 조건은 확인 필요다.
2. AC-02: 출생연도만으로 정확한 만 나이를 확정하지 않는다. 만 나이 경계를 고정 시점에서 검증한다.
3. AC-03: “학자금대출 없음”, “장애인이 아님”, 직업 부정을 긍정으로 추출하지 않는다.
4. AC-04: 본인 나이와 자녀·부모 나이를 분리한다. 주체가 불분명하면 확정 대신 재질문한다.
5. AC-05: 거주지와 직장, 과거와 현재를 분리한다. “부산 거주·서울 출근”은 부산이다.
6. AC-06: 이용횟수·등록·시험 종목이 미확인이면 지급 가능 합계로 확정하지 않는다. 금액 단위를 섞지 않는다.
7. AC-07: 모집 종료 후 신규 신청을 유도하지 않는다. 기존 신청의 승인·수령 사실 기록은 계속 가능하다.
8. AC-08: 수집 실패가 마지막 성공 본문을 지우지 않는다. 변경 발견은 검수 완료가 아니다.
9. AC-09: 동의 없는 발송과 실제 제공업체 없는 발송은 차단한다. 미리보기 클릭을 캠페인 전환으로 세지 않는다.
10. AC-10: 저장소 장애·미로그인 시 타인/데모 개인화 데이터를 정상 응답으로 제공하지 않는다.

모든 문장이 모든 수용 기준을 입증하지 않는다. 안전성 기준은 별도 통합 시험과 실사용 검수로 확장한다.

## 5. 데이터 모델과 지표 정의

### 데이터 사전

- user_profiles.user_id: Sites가 인증한 계정의 안정적 식별자. 클라이언트가 선택할 수 없다.
- profile_data: 최소 사용자 조건과 confirmedFields. 미확인 숫자 0/false를 사실로 쓰지 않는다.
- confirmed_at: 사용자가 저장한 시점. 공공기관이 자격을 확정했다는 뜻이 아니다.
- data_mode: 기존 행의 기본값 demo. 신규 계정은 pilot. 로컬 검증 저장소는 운영과 분리된다.
- benefit_applications: 사용자+혜택 유일키. 현재는 혜택 ID가 모집회차를 포함하는 대표 사례이며 반복 지급 원장은 아직 없다.
- expected_value: 해당 규칙 적용 시 계산 예시. received_amount와 합치지 않는다.
- received_amount/received_at/receipt_method: 실제 입력한 수령액·날짜·자기보고 여부. 서비스 이용은 service_self_report로 따로 기록하며 원화로 환산하지 않는다.
- rule_version: 판정에 사용한 규칙 버전. 코드 변경으로 배포하며 웹 검수 승인이 이 버전을 자동 변경하지 않는다.
- events.properties: 신청 ID, 이전/다음 단계, 규칙 버전 등. 원문 개인정보를 복제하지 않는다.
- source_reviews: 원문 URL, 전체 본문 해시, 앞 5,000자 발췌, 이전 성공 발췌, 발견·검수 시점, 의견. 메뉴·날짜 변화도 감지하므로 자격 변경 자동 판단 금지.
- portfolio_records: decision/research/experiment/campaign 근거. 사람·연락처 대신 익명 ID 사용.
- experiment_assignments: 사용자+실험 유일키. 한 번 배정한 A/B 그룹 유지. 배정은 실제 메시지 노출이 아니다.

|---|---|---|

| 반복 입력 수 | 이미 확인된 같은 조건을 다시 요구한 횟수 | 목표 0건. 자격 재확인이 법·기관상 필요한 경우는 별도 사유 기록 |
| 자기보고 수령액 | received_at과 self_report가 있는 received_amount 합 | expected_value 및 비현금 제외. 현재 화면은 내 계정 누계 |
| 사용자 단계 | 각 단계에 도달한 고유 user_id | 내 계정은 최대 1명. 여러 신청 건을 사람 수로 세지 않음 |
| 신청 시작 주차 | 최초 benefit_checking 이벤트 기준 UTC 연도-주차 | 감시 생성일을 준비 시작일로 사용하지 않음 |
| 7일 제출 | 준비 시작 후 0~7일 내 benefit_submitted가 있는 사용자-혜택 | 화면은 건수·관찰 완료 건수 표시. 미성숙 집단과 비율 혼합 금지 |
| 실험 준비 시작률 | 배정 후 7일 내 시작 고객 / 적격 배정 고객 | 실제 노출 전 효과 미측정. 10명에서 통계적 승자 선언 금지 |
| 알림 후 행동 귀속 | 유효 발송 클릭 후 7일 내 같은 혜택 준비 시작 | 실제 발송 ID 연동 전 미구현. 귀속은 인과효과가 아님 |
| 정정률 | 검수 후 정정된 판정 쌍 / 검수된 판정 쌍 | 현재 정의 단계. 원장 누락된 상태에서 0%로 표시 금지 |
| 신속성 | 게시→발견, 발견→검수, 검수→알림의 원시 시간 차 | 게시 시각 미제공은 unknown. 예정 주기를 측정된 지연으로 쓰지 않음 |

SQL 예시 (내보낸 데이터를 분석할 때도 동일한 기준 사용):

```sql
-- 자기보고 금액. 운영자/기관 확인액과 이름을 구분한다.
SELECT SUM(received_amount) AS self_reported_won
FROM benefit_applications
WHERE user_id = ? AND receipt_method = 'self_report'
  AND received_at >= ? AND received_at < ?;

-- 미리보기 반응은 실제 캠페인 보고에서 제외한다.
SELECT event_type, COUNT(*) AS events
FROM events WHERE user_id = ? AND event_type LIKE 'preview_%'
GROUP BY event_type;
```

## 6. CRM 운영과 실험

행동 세그먼트: 조건 미확인 / 준비 가능·미시작 / 마감 임박·준비 중 / 신청 후 확인 대기 / 변화 감시. 나이·지역은 각 세그먼트 안의 분석 차원이다.

공통 정책: 채널·목적별 동의 → 수신 중지 → 자격·접수 상태 → 현재 단계 → 한국시간 20~09시 조용한 시간 → 동일 사용자·혜택·사유·회차 중복 → 24시간 빈도 → 제공업체 발송. 현재 마지막 두 발송 정책은 실제 제공업체 연결 전 추가 검증이 필요하며, 제공업체가 없어 실제 발송은 항상 차단된다.

첫 실험: 같은 혜택·시점에서 금액 강조 A와 다음 행동 강조 B 비교. 고객 단위 고정 배정, 주지표는 7일 준비 시작, 보조는 14일 제출·마감 전 제출, 안전지표는 철회·오판정 신고·만료 혜택 발송이다. 실제 기준 전환율과 최소 의미 효과를 측정한 뒤 필요한 표본을 산정한다.

## 7. 5명 파일럿과 10명 확장 테스트 키트

첫 파일럿: 서울 거주 만 19~34세 직장인·구직자 중 최근 6개월 안에 정책·지원금 탐색 경험이 있는 5명. 마감이 있는 현금성 혜택을 대상으로 첫 혜택 도달, 조건 이해, 준비 시작과 중단 지점을 관찰한다. 제품의 전국·전 생애주기 범위를 줄이는 것이 아니라 첫 검증의 관찰 가능한 범위를 정하는 것이다.

확장 계획: 첫 파일럿의 중대한 문제를 수정한 뒤 학생·양육/가사 2명, 중장년·고령 또는 독거·돌봄 3명을 더해 누적 10명으로 확장한다. 가족이 대신 사용하면 직접 사용과 구분한다.

모집문 초안:
“흩어진 공공 혜택을 내 조건으로 확인하고 신청 준비를 이어가는 아하루프를 시험 중입니다. 약 40분 동안 화면을 사용하며 이해하기 어려운 점을 알려주실 분을 찾습니다. 실제 지원금 지급·선정이나 신청 대행은 제공하지 않습니다. 민감서류 제출은 요청하지 않으며 참여·중단은 자유입니다.”

동의 안내: 목적, 기록 범위, 익명화, 보관·삭제 기준, 중단 가능 여부를 참여 전에 설명한다. 녹음은 별도 선택 동의다. 연락처·주민번호·계좌번호·인증키를 사이트 기록에 넣지 않는다. 보관기간과 담당 연락창구는 실제 모집 전에 확정해야 한다.

40분 진행: 동의 5분 → 최근 실제 경험 10분 → 과제 20분 → 신뢰·부담·재사용 이유 5분.

인터뷰 질문: 최근 찾은 혜택은 무엇인지 / 어디에서 발견했는지 / 실제 무엇을 했고 어디서 멈췄는지 / 자격 판단에서 어려운 조건은 무엇인지 / 어떤 근거면 신청을 시작하는지 / 마감·서류를 어떻게 기억하는지 / 유료로 해결하고 싶은 구체적 일이 있었는지.

과제: 상황 입력 → 해석 조건 하나 수정 → 추천 이유·모르는 조건을 자기 말로 설명 → 준비 시작과 공식 서류 확인 → 동의 설정·진행 상태 변경.

기록 양식:
```
익명 ID / 생활 그룹 / 본인 또는 대리 / 참여 동의 / 녹음 동의
과제 / 도움 없이 성공 여부 / 도움 내용 / 소요 시간 / 중단 지점
관찰 발언 / 문제 심각도 / 개선안 / 연결 BA-ID / 후속 확인일
```

참여자 칸을 미리 성공으로 채우지 않는다. 검증실의 사용자 관찰 기록은 실제 관찰 후에만 작성한다. 현재 링크는 소유자 접근 범위를 유지하며 외부 참여자 초대는 접근 설정이 필요하다.

첫 파일럿 탐색 기준: 4/5명이 도움 없이 첫 혜택까지 도달하고, 4/5명이 `받을 가능성`과 `지급 확정`을 구분해 설명한다. 작은 표본의 성과지표가 아니라 문제 발견 기준이다. 3명 이상 같은 핵심 과제 실패, 개인정보 노출, 동의 없는 발송, 잘못된 자격 확정은 다음 모집 전 중단·수정한다. 누적 10명 확장 뒤에는 실제 관찰값으로 다음 목표를 다시 정한다.

## 8. 사업 판단과 운영 모델

2026-09-18 공식 자료 확인:

- [대한민국 공공서비스(혜택) API](https://www.data.go.kr/data/15113968/openapi.do): 무료, 개발 신청 트래픽 10,000, 정부·지자체 등 기본망. 사용자 활용 신청·인증키 필요.
- [복지로 중앙부처복지서비스 API](https://www.data.go.kr/data/15090532/openapi.do): 무료, XML, 개발 신청 트래픽 100. 개발 한도로 전체 상세를 매시간 갱신할 수 있다고 약속하지 않는다.
- [온통청년 API](https://www.data.go.kr/data/15143273/openapi.do), [실제 신청 가이드](https://www.youthcenter.go.kr/cmnFooter/openapiIntro/oaiGuide): 회원가입·로그인·인증키 신청·심사 절차. 실제 발급 전 연결 준비 상태 유지.

공식 API는 혜택 공고 정보이고 개인의 자격 확정·지급 내역 API가 아니다. 기관 게시→API 반영은 아하루프가 직접 통제하지 못한다. API 한도·이용약관·기관 반영 주기를 확인한 뒤 출처별 수집 주기를 정한다.

운영 역할: 수집 담당(실행·실패) → 정책 검수 담당(대상/금액/기간 대조) → 제품 담당(규칙·공지 변경 승인) → CRM 담당(동의·중복·문구·발송) → 분석 담당(분모·누락·피드백). 한 사람이 맡더라도 역할별 근거를 분리한다. 현재 검증실은 계정별 학습용 운영이며 조직 권한 분리는 미구현이다.

### 비용 시나리오

가정: 200개 혜택, 월 1회 검수, 내부 시급 20,000원, 인프라 월 50,000원. 초기 개발비·메시지·세금 제외. 견적이 아니다.

| 방식 | 시간 가정 | 월 비용 예시 |
|---|---|---|
| 기관 페이지 직접 수집 | 유지 20시간 + 건당 5분 | 783,333원 |
| 공식 API + 검수 | 유지 8시간 + 건당 3분 | 410,000원 |
| 제휴 | 유지 4시간 + 건당 2분 | 263,333원 + 제휴비 Q |

이 가정에서는 Q가 약 146,667원 이하여야 API 방식보다 저렴하다. 2,000건으로 확대하면 API 검수도 100시간이 되므로 변경 필드 중심 검수의 가치가 커진다. 실제 2주 작업시간을 기록해 가정을 대체한다.

수익 가설: 이용자 구독 / 기관·기업 안내 운영 / 명확히 표시한 제휴 광고 / 범위가 정해진 신청지원. 현재는 무료 검증을 권고하며 지불의사·계약을 매출처럼 표현하지 않는다.
