# sta-improve : 완성한 다음, 한 조각 더 키우기

## 목적

참가자가 일단 한 번 완성한 결과물을 놓고, 개선 후보를 생각하고 그중 하나를 골라 남은 시간에 맞춰 구현하도록 돕는다. 한 번의 개선에는 30분을 기본 예산으로 배정하되 완료 시간을 약속하지 않는다.

이 스킬은 다른 스킬과 결정적으로 다르다. `$sta-define-problem`과 `$sta-make-prd`는 좁히는(수렴) 도구다. 막막함을 오늘 크기로 줄여 완성에 데려다준다. `$sta-improve`는 반대로 다시 넓히는(발산) 유일한 도구다.

> 왜 여기서 발산하나 : 빈 종이 위의 "뭐 만들지"는 비개발자에게 공포지만, 이미 돌아가는 내 결과물 위의 "뭘 더 해볼까"는 신남이다. 완성이 곧 생각을 넓히는 연료가 된다. "오 이게 되네? 그럼 이것도 되나?" 그 순간을 만드는 것이 이 스킬이다.

## 발동 신호

- 첫 완성 직후 : "다 됐어요", "첫 30분 목표 됐어요", "화면에 떴어요", "리포트 열렸어요"
- "이제 뭐 더 해볼까요", "기능 더 붙이고 싶어요", "개선하고 싶어요", "더 좋게"
- "다 만들었는데 뭔가 아쉬워요"
- 강사가 "다음에 붙일 것 3개"를 적으라고 안내했을 때

아직 아무것도 완성 안 됐으면 이 스킬을 쓰지 않는다. `$sta-define-problem` / `$sta-make-prd`로 먼저 하나를 완성시킨다. 개선은 그다음이다.

## 진행 원칙 (반드시 지킬 것)

1. 먼저 직접 써보게 한다. 개선 아이디어는 머리가 아니라 손에서 나온다
   > "고치기 전에, 방금 만든 걸 한 번 직접 써보세요. 파일 열어보고, 버튼 눌러보고요. 써보니 어떤 점이 제일 아쉬웠어요?"
2. 발산은 짧게, 메뉴로 펼친다. 자료조사를 시키지 않는다. 고를 수 있게 보기를 차려준다 (아래 "🌱 발산 메뉴")
3. 그다음 반드시 다시 좁힌다. 여러 개가 나와도 오늘 더 할 것은 딱 하나. 나머지는 적어두고 미룬다
4. 참가자가 고른다. 정해지지 않았으면 "선택 대기"로 적고 대신 고르지 않는다
5. 개선 하나를 고르고 남은 시간을 확인한다. 저장, 로그인, 페이지 추가를 어렵다는 이유만으로 빼지 않는다. 현재 구현 상태와 실제 소요 시간을 기준으로 판단한다 (아래 "⏱️ 개선 시간 예산 점검")
6. 진행 단계를 매번 표시한다. 예 : `[개선 1] 무엇을 더할지 고르기`
7. 구현할 때는 현재 결과를 보존한 새 버전 파일에서 한다 (AGENTS.md 저장 규칙). 예 : `kakao-report-2026-09-08-v02.html`. 프로젝트 폴더(`projects/주제-날짜-v01/`)에서 작업 중이면 그 안에 새 버전을 만든다
8. 한 조각 끝나면 멈춰서 축하하고, 계속할지 묻는다. 자동으로 다음 개선으로 달리지 않는다
9. 막히거나 에러가 나면 `$sta-clarify`, 그래도 안 되면 `$sta-sos`

아이디어 정리만 요청받았다면 구현하지 않는다.

## 진행 흐름 (이 순서로)

### `[개선 1]` 써보고 => 아쉬운 점 한 가지 찾기
- 결과물을 직접 만져보게 한 뒤, 딱 하나 아쉬운 점을 꺼낸다
- 안 떠오르면 객관식으로 돕는다
  > "보통 이런 게 아쉬우시더라고요. 가까운 거 골라보세요.
  > ① 보기가 좀 밋밋해요 ② 이런 기능도 있으면 ③ 쓰기가 좀 번거로워요 ④ 결과가 좀 부족해요"

### `[개선 2]` 넓히기 : "그럼 이런 것도 돼요" (발산)
- 기획서의 "나중에 추가할 것"이 있으면 먼저 펼쳐 보여준다. `$sta-make-prd`가 일부러 적어둔 목록이다
  > "예전에 '나중에' 하자고 적어둔 것들이 여기 있어요. 이제 하나 꺼내볼 때가 됐네요."
- 거기에 "🌱 발산 메뉴"에서 한두 개를 곁들여 후보 3개를 만든다. 각 후보가 누구에게 어떤 도움이 되는지 쉽게 설명한다

### `[개선 3]` 좁히기 : 오늘 더 할 딱 하나 고르기 (수렴)
- 나온 것 중 하나만 선택하게 한다
  > "좋아요, 다 적어뒀어요. 그중 오늘 딱 하나만 더 해볼까요? 어떤 게 제일 끌려요?"
- 고른 하나의 크기를 점검한다 (아래 표). 크면 더 쪼갠다
- `작업일지.md`에 아래 형식으로 덧붙인다. 기존 기록은 보존한다. 별도 아이디어 파일은 만들지 않는다

```markdown
## 2026-09-08 (day01) : 개선 후보
- 후보 3개 : ① 시간대별 답장 속도 표 ② 이모티콘 빈도 ③ 결과 복사 버튼
- 고른 1개 : ③ 결과 복사 버튼
- 이유 : 매번 결과를 옮겨 적는 게 제일 번거로움
```

시간이 없어 고른 하나를 오늘 못 붙여도 이 기록은 남긴다. 다음 실습의 출발점이다.

### `[개선 4]` 만들기 => 눈으로 확인 => 축하
- 고른 한 조각을 새 버전 파일에 만들고, 바로 화면이나 파일에서 확인시킨다. 어디를 열어 무엇이 보이면 되는지 적는다
- 잘 되면 충분히 축하하고 계속할지 갈림길을 제시한다 (아래 "마무리")

## 🌱 발산 메뉴 (이렇게 차려서 고르게 한다)

참가자가 스스로 조사하게 하지 말고 아래에서 골라 상상하게 한다. "이런 것도 만든 분 계셨어요" 식으로 곁들이면 더 잘 떠올린다.

| 방향 | 한 마디로 | 예 |
|---|---|---|
| 🎨 보기 좋게 | 같은 기능, 더 예쁘게 | 색과 글꼴 정리, 카드 모양, 모바일에서도 잘 보이게 |
| ➕ 기능 하나 더 | 기획서 "나중에"에서 꺼내기 | 검색 추가, 필터, 항목 더 보여주기, 시간대별 표 |
| ⚡ 더 편하게 | 손 가는 걸 줄이기 | 복사 버튼, 입력 자동 채우기, 결과 바로 저장 |
| 🧠 더 똑똑하게 | AI를 한 스푼 더 | 요약 품질 올리기, 자동 분류, 어울리는 문구 제안 |
| 📤 남도 쓰게 | 혼자 => 여럿 | 파일이나 폴더로 전달하기 쉽게 정리. 인터넷 주소가 필요하면 강사와 확인 |

막판에 욕심이 커지면(여러 개를 한 번에) `[개선 3]`으로 돌아가 딱 하나로 다시 좁힌다.

## ⏱️ 개선 시간 예산 점검

개선도 전체 실습 시간에 포함한다. 현재 시각과 실습 종료 시각을 확인하고, 마지막 30분의 마무리 시간을 제외한 여유가 있을 때 진행한다. 이미 종료 시각을 알고 있으면 다시 묻지 않는다. 핵심 기능이 아직 미완성이면 먼저 완성한다.

30분은 구현과 오류 수정, 동작 확인을 포함한 작업 예산이다. 빠르게 끝나면 다음 작업을 검토하고, 지연되면 실제 진행 결과에 따라 조절한다. 개선 횟수를 미리 정해 채우지 않는다. 기능 이름만으로 30분 안에 끝난다고 판단하지 않는다.

### 한 번에 하나씩 검토할 개선 후보
- 화면에 버튼이나 표시 하나 추가
- 있는 기능을 다듬기 (보기 좋게, 복사 되게)
- 화면(페이지) 하나 더 만들기
- 입력한 것을 저장해두기. 목록으로 다시 보기
- 로그인 붙이기
- AI 기능 하나 얹기 (요약, 분류)
- 기획서 "나중에" 목록의 항목 하나

### 나눠야 할 신호 (🚩)
- ⏳ 심사나 승인 대기가 필요 (앱스토어, 카톡 알림톡)
- 💳 결제(PG), 사업자 등록이 필요
- "그리고 ~도, ~도" (한 바퀴에 여러 개)
- 오류 수정이나 연동이 예상보다 오래 걸려 마무리 시간을 침범할 우려

🚩면 "안 됩니다"가 아니라 3박자로 나눈다. 오늘 여기까지 됩니다 => 더 가려면 이런 대가 => 일단 이걸로 갈게요. 미룬 것은 기획서 "나중에 추가할 것"과 `작업일지.md`에 적어둔다. 버리지 않고 다음 바퀴로 미룬다.

## 나선으로 돈다 (이 스킬의 자리)

이 워크샵의 흐름은 깔때기(한 번 좁히고 끝)가 아니라 나선이다.

```
define-problem => make-prd => 만들기 => ★첫 완성★
                                          ↓
                                    sta-improve
                             (써본다 => 넓힌다 => 하나 고른다 => 더 만든다)
                                          ↓
                                   ★한 단계 자란 결과물★ => 또 improve / 또는 여기서 멈춤
```

핵심 기능이 동작하고 마무리 시간을 제외한 여유가 있으면 다음 개선을 제안한다.

## 진행 예시 (이렇게 대화한다)

> **Codex**: 첫 버전 완성 축하해요. 고치기 전에 방금 만든 리포트를 한 번 직접 열어보세요. 숫자도 보고, 표도 보고요. 써보니 어떤 점이 제일 아쉬웠어요?
>
> **참가자**: 음… 결과가 나오긴 하는데 복사하기가 좀 귀찮아요.
>
> **Codex**: 좋은 포인트예요. `[개선 2]` 예전에 '나중에 하자'고 적어둔 것도 같이 볼까요?
> 거기 ① 시간대별 답장 속도 표 ② 이모티콘 빈도가 있었고, 방금 말한 ③ 복사 버튼도 있겠네요.
> `[개선 3]` 오늘은 딱 하나만 더 해볼게요. 제일 끌리는 거 골라주세요. 나머지는 작업일지에 적어둘게요.
>
> **참가자**: 복사 버튼이요. 제일 자주 쓸 것 같아서.
>
> **Codex**: 작업일지에 적었어요. `[개선 4]` 기존 리포트는 그대로 두고 v02 파일에 복사 버튼을 추가할게요.
> … (완성) … `day01/output/kakao-report-2026-09-08-v02.html`을 열면 결과 옆에 '복사' 버튼이 있어요. 눌러서 잘 복사되는지 보실래요?

## 마무리 : 한 조각 끝나면 갈림길 제시

개선 하나가 화면에서 동작하면 충분히 축하하고, 자동으로 다음으로 달리지 말고 갈림길을 가볍게 제시한다.

1. 🔁 한 바퀴 더 (마무리 시간을 제외한 여유가 있을 때만) : "또 하나 더 해볼까요? 방금 적어둔 '나중에' 목록에서요." => 이 스킬을 다시
2. ✋ 여기서 멈추기 : "오늘은 여기까지! 남은 아이디어는 작업일지에 적어뒀어요. 다음에 `$sta-improve`로 이어가면 돼요."

멈추는 것도 좋은 선택이다. 작은 완성을 여러 번이 큰 미완성보다 백 배 낫다.

## 참고

- 크기 판단 => `$sta-define-problem`의 "🪓 크기 가늠하기". 미룬 것은 기획서 "나중에 추가할 것"에
- 막혔을 때 => `$sta-clarify`, 그래도 안 되면 `$sta-sos` (강사 호출)
