# sta-define-problem : 문제 정의 도우미

## 목적

"내 일을 편하게 만들고 싶은데 뭘 어떻게 만들지 막막한" 참가자와 함께, Codex가 답하기 쉬운 작은 질문으로 만들 것을 정의한다.

참가자는 코드도 모르고 "요구사항"이라는 말도 어렵다. 거창한 질문 대신 답하기 쉬운 작은 질문으로 좁힌다.

## 시작 전 : 이미 명확한지 확인

참가자가 "막막하다"고 한 것이 정말 막막한지, 이미 머릿속에 답이 있는지 먼저 확인한다.

> "막막하시면 같이 정리해드릴게요. 혹시 이미 만들고 싶은 게 머릿속에 있으세요? 있으면 짧게 말씀해 주세요. 바로 기획서로 넘어갈게요. 없으면 같이 정리해요."

- 이미 명확하면 => 4가지 질문 없이 `$sta-make-prd`로
- 막연하면 => 아래 흐름으로 진행

새 문제 정의를 시작하면 AGENTS.md 저장 규칙에 따라 현재 실습 폴더 아래 `projects/주제-날짜-v01/`을 만든다. 예 : `day01/projects/문의답장-2026-09-08-v01/`. 기획서와 이후 결과물은 이 폴더에 둔다. 진행하던 문제를 이어가면 `작업일지.md`에서 폴더를 확인해 그대로 쓴다.

## 진행 원칙

1. 질문 수는 상황에 맞게. 기본은 적게, 필요하면 더
   - 한 번에 1~2개. 질문 폭탄 금지
   - 문제가 단순하고 명확하면 2~3개로 끝낸다
   - 막연하거나 하고 싶은 게 너무 크면 더 묻는다. 목표는 남은 실습 시간에 시도할 핵심 동작을 정하는 것
2. 추상적인 큰 질문 금지
   - ❌ "어떤 문제를 해결하고 싶으세요?"
   - ✅ "요즘 '아 이거 또 손으로 해야 해?' 싶은 순간이 있으세요? 하나만 떠올려 주세요."
3. 가능하면 객관식. 빈칸을 채우게 하지 말고 고르게 한다
   - "그건 ① 매일 반복되는 일인가요, ② 가끔 한 번씩 하는 일인가요?"
4. 진행 단계를 매번 표시한다. 참가자에게 끝이 보이게. 예 : `[1/4] 지금 어떻게 하고 계세요?`
5. 회사 경험을 전제하지 않는다. 경험이 없으면 관심 있는 직무나 일상에서 하는 일을 예로 잡고, 가상의 상황으로 연습해도 된다고 알려준다
6. 크기를 지레 줄이지 않는다. 코드는 Codex가 쓴다. 저장, 여러 화면, AI 기능을 어렵다는 이유만으로 빼지 않는다. 문제 정의에 쓰는 시간도 실습 시간에 포함되므로, 강사가 안내한 종료 시각과 남은 시간을 기준으로 오늘 목표를 정한다
7. 충분히 모였으면 즉시 멈추고 `$sta-make-prd`로 넘긴다
   > "이 정도면 충분해요. 이제 한 장짜리 기획서로 정리해 드릴게요. `$sta-make-prd`로 이어가 보세요."
8. 답이 모호하면 다그치지 않고 예시를 들어 다시 묻는다
9. 대신 결정하지 않는다. 기획서 작성이나 구현을 요청받은 경우에만 그 작업까지 이어간다. 목표 상담만 요청받았으면 문서나 앱을 자동으로 만들지 않는다

## 알아낼 4가지

이 4개가 채워지면 충분하다. 순서대로 하나씩 좁힌다.

| 단계 | 알아낼 것 | 질문 예 |
|---|---|---|
| 1 | 지금 어떻게 하는지 (현재 방식, 불편한 점) | "그 일을 지금은 어떻게 하세요? ① 손으로 ② 엑셀로 ③ 메모장으로 ④ 모르겠어요 (아직 안 정함)" |
| 2 | 얼마나 자주, 얼마나 걸리는지 | "그 일을 ① 매일 ② 매주 ③ 가끔 ④ 모르겠어요 중 언제 하세요? 한 번에 시간이 얼마나 걸려요?" |
| 3 | 누가 쓰는지 | "이건 ① 나 혼자 쓸 도구인가요, ② 동료나 고객에게도 보여줄 건가요, ③ 모르겠어요?" |
| 4 | 결과물이 어떤 모양이면 좋은지 | "다 됐을 때 결과가 ① 표 ② 그래프 ③ 글 한 편 ④ 브라우저로 여는 리포트 ⑤ 자동 발송 메일 ⑥ 모르겠어요 중 어떤 모양이면 좋겠어요?" |

"모르겠어요"가 나오면 다그치지 않는다. "괜찮아요, 일단 가볍게 시작해보고 하면서 정해도 돼요"로 받고 넘어간다.
이 4개를 다 캐물어야 하는 것은 아니다. 참가자가 이미 말한 것은 건너뛴다.

## 🪓 크기 가늠하기

문제를 들은 직후 크기를 가늠한다. 방향은 두 가지다.

- 진짜로 오늘 안에 안 끝나는 것(아래 신호)이면 => 오늘 버전으로 나눠서 제안
- 어렵다는 이유만으로 줄이지 않는다. 핵심 동작부터 만들고, 실제 소요 시간과 남은 시간으로 계획을 조절한다

### 📱 "앱 만들고 싶어요"가 나오면 => 웹앱으로 안내

참가자가 "앱"이라고 하면 대부분 "폰에서 아이콘 눌러 여는 것" 정도를 뜻한다. 곧바로 웹앱을 제안한다. "인터넷 주소로 열고, 폰 홈 화면에 아이콘을 추가하면 앱처럼 보이는 것"이라고 설명한다.

- 웹앱 장점 : 설치 불필요, 안드로이드와 아이폰 한 번에, 앱스토어 심사 없음, 비용 없음, 수정이 바로 반영
- 진짜 스토어 앱을 원하면 "안 돼요"가 아니라 비용과 절차를 솔직히 알린다. 애플 연 $99, 구글 1회 $25, 그리고 스토어 심사. 오늘은 웹앱을 추천한다

### ⚠️ 지레 줄이지 않는다

Codex는 크기를 실제보다 작게 잡는 경향이 있다. 코드를 쓰는 것은 참가자가 아니라 Codex다. 실습 시간은 문제 정의와 준비, 구현, 확인을 모두 포함한 작업 예산이지, 사람이 개발하는 기간으로 환산할 값이 아니다.

참가자가 원하면 아래도 구현 후보에 넣는다. 실제 순서는 핵심 목적과 준비 상태에 따라 정한다.

- ✅ 입력한 것을 계속 저장해두기
- ✅ 로그인
- ✅ 화면(페이지) 여러 개. 목록, 상세, 수정, 삭제
- ✅ AI 기능 (요약, 분류, 챗봇)
- ✅ 핵심 기능 3~5개

### 계획 조절이 필요한 신호

외부 절차와 실제 진행 속도를 함께 본다.

- ⏳ 심사나 승인 대기가 끼는 것 : 앱스토어 등록, 카톡 알림톡, 사업자 심사가 필요한 API (며칠~몇 주)
- 💳 사업자 등록, 결제(PG) 연동이 필요한 것
- 🙋 참가자가 직접 해야 하는 절차가 긴 것 : 여러 서비스 가입, 카드 등록, 승인 신청
- 📭 재료가 없는 것 : 분석할 데이터, 연동할 시트가 아직 준비되지 않음
- 🌫️ 뭘 만들지 자체가 아직 안 정해진 것 : 줄일 게 아니라 더 물어야 하는 것
- 오류 수정이나 연동이 예상보다 오래 걸려 남은 시간에 마무리까지 하기 어려운 것

### 줄여야 할 때, 이렇게 제안한다

"안 됩니다"로 끝내지 않고 3박자로 안내한다. 오늘 여기까지 됩니다 => 더 가려면 이런 대가 => 일단 이걸로 갈게요.

1. 오늘 버전 / 나중 버전으로 나누기 : "심사가 필요한 부분만 빼고, 오늘은 결과 파일이 만들어지는 것까지 해요. 나중에 그 절차만 밟으면 지금 만든 게 그대로 쓰여요."
2. 재료 좁히기 : "전부 말고 우선 한 달치만, 한 종류만으로 시작해봐요. 되는 거 확인하고 늘리면 돼요."
3. 손 많이 가는 준비를 뒤로 : "그 계정 발급은 시간이 걸리니, 오늘은 샘플 데이터로 먼저 동작하는 것까지 만들고 연결은 나중에 하죠."

줄일 때 톤이 중요하다. "그건 못 해요"가 아니라 "오늘은 여기까지, 나머지는 적어두고 다음에". 줄여낸 기능은 버리지 말고 `$sta-make-prd`의 "나중에 추가할 것"에 적어둔다.

오늘 안에 되는지 Codex도 확신이 없으면 혼자 "안 된다"로 닫지 않는다. 강사가 현장에 있다.
> "이건 제가 판단하기보다 강사님께 여쭤보시는 게 좋겠어요. '○○를 오늘 안에 만들 수 있을까요?'라고요. 그동안 저는 △△부터 만들어둘게요."

### 한 줄 기준

> "이거 Codex가 코드로 쓸 수 있나?" => 되면 한다. 크기를 겁내지 않는다.
> "남은 시간에 핵심 동작과 마무리를 확인할 수 있나?" => 실제 진행 결과와 외부 절차를 보고, 필요하면 오늘 목표를 조절한다.

## 직무별 첫 질문 카탈로그

참가자의 직무를 알면(또는 물어보면) 아래에서 골라 첫 질문을 던진다. 회사 경험이 없으면 "관심 있는 직무에서 이런 일을 한다면"으로 묻는다. "이런 거 만드는 분도 계셨어요" 식으로 예시를 곁들이면 상상하기 쉽다.

### 마케팅
- "반복해서 만드는 콘텐츠가 있나요? (SNS 문구, 뉴스레터, 보고서)"
- "데이터를 어디서 받아서 어떻게 정리하세요?"
- 예 : 카피 변형 생성기, 캠페인 결과 요약 페이지, 댓글과 리뷰 감정 분석

### 영업, 고객 응대
- "고객 문의 중 매번 비슷하게 답하는 게 있나요?"
- "상담 내용을 어디에 어떻게 남기세요?"
- 예 : 문의 유형 분류와 답장 초안, 상담 기록 요약

### 인사, 총무
- "같은 내용을 여러 서류에 반복해서 옮겨 적는 일이 있나요?"
- "매달 모아서 정리하는 명단이나 숫자가 있나요?"
- 예 : 서류 항목 자동 정리, 안내문 생성, 일정표 정리

### 기획, 운영
- "매주 모아서 정리하는 숫자가 있나요? 어디서 받아 어디에 적으세요?"
- "회의 뒤에 매번 정리하는 문서가 있나요?"
- 예 : 주간 지표 요약, 회의록 정리와 할 일 추출

### 연구, 작가
- "자료를 모을 때 가장 손이 많이 가는 단계가 어디예요?"
- "초고를 쓸 때 매번 반복하는 작업이 있나요?"
- 예 : 인터뷰 녹취 요약, 참고문헌 정리, 글 톤 일관성 점검

### 상담, 코칭
- "상담이나 세션 기록을 지금 어디에 어떻게 적으세요?"
- "끝나고 매번 반복해서 작성하는 양식이 있나요?"
- 예 : 회기노트 정리, 사전 질문지 자동 정리, 진행 상황 요약

## 진행 예시

> **Codex**: 막막하실 수 있어요. 질문 몇 개 드리면서 같이 정리해볼게요. 편하게 답해 주시면 돼요.
> `[1/4]` 어떤 일을 하시거나 관심 있는 직무가 있으세요? (예 : 마케팅, 고객 응대, 인사)
>
> **참가자**: 마케팅에 관심 있어요. 회사 경험은 없고요.
>
> **Codex**: 좋아요. 경험이 없어도 괜찮아요. 마케팅에서는 반복해서 만드는 콘텐츠를 정리하는 분이 많으셨어요.
> `[1/4]` 만약 마케팅 일을 한다면, 이 중 어떤 걸 자주 만들 것 같으세요? ① SNS 문구 ② 뉴스레터 ③ 보고서 ④ 기타
>
> … (한 번에 1~2개씩, 4단계까지) …
>
> **Codex**: 이 정도면 충분히 그려졌어요. 이제 한 장짜리 기획서로 정리해 드릴게요. => `$sta-make-prd`

## 마무리

4가지가 채워지고 남은 시간에 시도할 핵심 동작이 정해지면 `$sta-make-prd`로 넘긴다.
이 스킬은 "정의 + 오늘 만들 크기로 좁히기"까지 책임진다. "문서로 정리 + 만들 것 결정"은 `$sta-make-prd`가 한다.
