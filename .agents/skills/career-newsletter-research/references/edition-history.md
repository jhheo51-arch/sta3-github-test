# Edition comparison and history

Read this when an earlier newsletter or delivery record is available. Compare events and claims, not just titles or URLs.

## Same-day repeat request

When the user requests another edition on the same date:

1. Read the latest same-day edition first.
2. Exclude an event when its underlying facts and implications have not materially changed.
3. When the same event only gains another corroborating source, update its evidence and verification status rather than creating a new item.
4. When a function, metric, schedule, policy, customer result, or released artifact materially changes, label it `후속 업데이트` and show the previous known state, the new change, and why the difference matters.
5. When no qualified material change exists, do not repeat the earlier newsletter. Return `새로운 주요 변화 없음` with only any minor verification updates.
6. Label a relevant older event found for the first time as `새로 발견한 자료`, not `신규 발표`.

## Requests after one or more skipped days

- Compare with the latest delivered edition, not merely the previous calendar day.
- Keep unchanged events excluded even when they still fall inside the seven-day search window.
- If several updates occurred while no newsletter was requested, combine them into one latest-state follow-up and summarize the change from the last delivered state.
- A different event that reinforces an earlier theme may appear as a new item. Label the theme `반복 신호` and do not reprint the old event.
- If an old event becomes more credible only because of new corroboration, update its verification status. Promote it to a highlight only when the new evidence materially changes the career implication, and label that change.
- If the latest delivered edition cannot be accessed, disclose that comparison could not be completed; do not claim the edition is deduplicated against history.

## Event identity

Use a stable event key based on the organization, product or program, core claim or action, and effective or event date. Canonical URLs help identify an event but do not define it.

For each delivered edition, retain when possible:

- cutoff date and delivery time
- path or destination link
- comparison-base edition
- event key and first-seen date
- status: `신규`, `후속 업데이트`, `반복 신호`, `새로 발견한 자료`, or `변경 없음`
- strongest source URLs and verification status

## Reader-facing history

When the delivery format supports navigation, provide `지난 뉴스레터` access. List real delivered editions by date and time, newest first. Do not list design revisions as separate editions. Show new and follow-up counts only when they are known.
