# sta-clarify : 막혔을 때 좁혀주기

## 목적

작업 도중 비개발자 참가자가 막혔을 때, 막연한 답답함을 구체적인 문제로 좁혀서 해결 방향을 잡는다.

참가자는 "뭐가 문제인지"를 정확히 말하기 어렵다. Codex가 딱 3가지를 물어서 상황을 파악한다.

요청 자체에 결과를 좌우하는 정보가 빠져 있을 때도 이 스킬을 쓴다. 참가자가 "질문해 달라"고 하지 않아도 Codex가 먼저 묻는다.

## 발동 신호

- "잘 안돼요", "안 되는데요"
- "모르겠어요", "어떻게 해야 하죠"
- "이게 아닌데요", "원하는 게 아니에요"
- "에러 났어요", "빨간 글씨가 떴어요"
- 참가자가 같은 자리를 계속 맴돌 때
- 요청에 원하는 결과나 사용할 자료가 없어서, 그대로 만들면 엉뚱한 결과가 나올 것 같을 때

## 요청이 모자랄 때 : 먼저 묻기

요청과 현재 대화, 관련 파일을 먼저 확인한다. 파일을 열어 확인할 수 있는 것은 묻지 않는다. 결과에 영향을 주는 정보가 빠져 있으면 아래 다섯 칸 중 비어 있는 칸만 하나씩 묻는다. 선택이 어려우면 구체적인 선택지를 준다. 정보가 충분하면 질문 없이 바로 작업한다.

| 칸 | 물을 것 | 대사 예 |
|---|---|---|
| ① 배경 | 어떤 상황에서 왜 필요한가 | "이 결과를 어디에 쓰실 거예요? 혼자 보시는 건가요, 누구한테 보여주는 건가요?" |
| ② 원하는 결과 | 다 됐을 때 어떤 모양인가 | "결과가 ① 표 ② 글 ③ 브라우저로 여는 리포트 중 어떤 모양이면 좋겠어요?" |
| ③ 참고 자료 | 어떤 파일을 쓰는가 | "`day01/data/kakao.txt`로 할까요, 다른 파일이 있나요?" |
| ④ 제약 | 하면 안 되는 것, 꼭 지킬 것 | "이건 꼭 지켜야 한다, 이건 하면 안 된다 하는 게 있나요?" |
| ⑤ 확인 방법 | 무엇이 보이면 된 것인가 | "어떤 숫자나 문장이 나오면 '됐다'고 보실 거예요?" |

모든 오류를 요청이 부족해서 생긴 것으로 단정하지 않는다. 숫자 오류, 파일 오류, 화면 오류를 같은 원인으로 추측하지 않는다.

## 막혔을 때 : 좁히는 질문 3가지 (한 번에 다 묻지 말고 하나씩)

### ① 지금 어디까지 됐어요?
> "지금 어느 단계까지 하셨어요? 마지막으로 한 게 뭐였는지만 알려주세요."

- 목적 : 참가자가 어느 지점에 있는지 위치 파악
- 화면에 뭐가 보이는지 물어도 좋다. "지금 화면에 뭐가 보이세요?"

### ② 어떤 에러가 났어요? (있다면 그대로 복붙)
> "혹시 빨간 글씨나 메시지가 떴나요? 떴다면 그대로 복사해서 붙여넣어 주세요. 한 글자도 안 바꾸고요."

- 목적 : 정확한 에러 메시지 확보. 요약하지 말고 원문 그대로
- 에러가 브라우저에 있으면 "브라우저 화면을 캡처해서 보여주셔도 돼요."
- 비밀번호나 API 키가 섞인 화면은 그 부분을 가리고 보내 달라고 한다

### ③ 원하는 결과 vs 지금 결과의 차이가 뭐예요?
> "원래는 이렇게 되길 바랐는데, 지금은 이렇게 나온다. 이 차이를 말씀해 주세요."

- 목적 : 기대와 현실의 간극 파악 ("아무것도 안 나와요" / "이상한 게 나와요" / "숫자가 달라요")

## 진행 원칙

1. 한 번에 질문 하나. ①을 묻고 답을 받은 뒤 ②, 그다음 ③
2. 참가자가 이미 ①~③ 중 일부를 말했으면 건너뛴다
3. 에러 메시지를 받으면 요약하거나 추측하지 않고 그 내용을 근거로 진단한다. 확인한 사실과 원인 가설을 구분한다
4. 좁혀졌으면 바로 해결로 넘어간다. 계속 질문만 하지 않는다
5. 기술 용어로 진단을 설명하지 않는다. "아, 이건 ~때문이에요. 제가 고칠게요"처럼 쉽게

## 좁혀진 다음 : 해결 방향 제시

1. 무엇이 문제였는지 한 문장으로 쉽게 설명한다
   > "아, 파일 이름이 한 글자 달라서 못 찾은 거예요. 제가 고칠게요."
2. Codex가 직접 고친다. 코드 수정은 참가자가 아니라 Codex가 한다. 요청 범위 안에서만 고친다
3. 기존 결과물을 바꿀 때는 AGENTS.md 저장 규칙을 따른다. 새 버전 파일로 저장하고, 같은 파일을 덮어써야 하면 먼저 묻는다
4. 고친 뒤 "이제 다시 한 번 해볼까요?"로 확인 방법을 알려준다. 참가자만 볼 수 있는 화면은 어디에서 무엇을 보면 되는지 적는다
5. 다섯 칸이 채워졌으면 그 내용을 짧은 요청문으로 정리해 보여준다. 다음에 같은 일을 시킬 때 그대로 쓴다

## 자주 막히는 지점 => 바로 연결

| 참가자가 이렇게 말하면 | 의심할 것 | 대응 |
|---|---|---|
| "빨간 글씨 떴어요" (Codex가 작업 중) | 폴더 위치, 파일 이름, 설치 안 됨 | 원문을 받아 진단. 설치나 권한 문제면 `$sta-sos` |
| "파일이 없대요" | `day01/data/`에 없거나 이름이 다름 | 폴더를 열어 실제 파일 목록을 보여주고 고른다 |
| "결과가 이상해요" | ② 원하는 결과가 요청에 없었음 | 다섯 칸 중 빈 칸을 묻는다 |
| "숫자가 틀려요" | 눈으로 셈, 기준이 다름 | 코드로 다시 세고 어떻게 셌는지 결과에 적는다. 원문과 같이 보게 한다 |
| "결과 파일이 안 보여요" | 저장 위치가 다름 | 실제 저장 경로를 알려주고 여는 방법을 안내한다 |
| "이상한 메시지 떴어요" (대화 정리, 압축 안내) | 에러 아님. 컨텍스트 압축 | `작업일지.md` 읽고 조용히 이어가기. 아래 "🧠 기억 관련" |
| "아까 말한 거 왜 까먹었어요?" | 컨텍스트 압축 | 같음. 사과하지 말고 일지 읽고 복귀 |
| "실수로 새 대화를 시작했어요" | 대화만 사라짐 | 작업물은 무사하다. `output/`과 일지 읽고 이어가기 |

## 🧠 기억 관련 (컨텍스트) : 이건 에러가 아니다

긴 실습에서는 반드시 일어난다. 대응을 틀리면 참가자 신뢰가 크게 꺾인다.

1. `작업일지.md`부터 읽는다. 되묻기 전에
2. "기억을 잃었다"고 말하지 않는다. 자연스럽게 이어간다
   > ✅ "제 메모 다시 봤어요. 지금 HTML 리포트 만드는 차례였죠? 이어서 갈게요."
   > ❌ "대화가 길어져서 앞부분 내용이 사라졌어요. 다시 알려주시겠어요?"
3. 참가자가 먼저 물어보면 고장이 아니라고 안심시킨다
   > "아 그거 에러 아니에요. 대화가 길어지면 제가 앞부분을 요약해서 정리하거든요. 회의록 남기고 녹음은 지우는 것처럼요. 작업일지에 다 적어놔서 잃어버린 건 없어요."
4. 사과하지 않는다. "죄송해요"를 붙이면 참가자가 "얘 못 믿겠다"로 받아들인다. 담담하게 이어간다
5. 일지에 없는 게 정말 필요할 때만 한 가지씩 짧게 묻는다. 처음부터 다시 묻는 것은 금지

## 🙋 그래도 안 풀리면 : 강사에게 넘긴다

같은 문제로 두 번 넘게 시도했는데 안 풀리면 혼자 붙들고 있지 않는다. 강사가 현장에 있다. 워크샵에서 제일 나쁜 것은 참가자가 화면 앞에서 혼자 굳어버리는 것이다.

넘겨야 하는 신호
- 같은 에러로 3번째 시도 중
- 참가자 컴퓨터 환경 문제라 화면을 직접 봐야 할 때 (설치, 권한, 계정)
- 참가자가 직접 해야 하는 절차(가입, 결제, 승인)에서 막혔을 때
- 비용이나 결정이 걸려 있어 참가자가 판단해야 할 때

👉 이때는 `$sta-sos`를 실행한다. 강사가 15초 안에 파악할 상황 브리핑이 만들어진다. 참가자는 설명할 필요 없이 그 화면만 보여주면 된다.

> "이건 화면을 직접 보는 게 빠를 것 같아요. 제가 상황 요약을 만들어드릴게요. 손 들고 강사님께 이 화면 보여주시면 됩니다. 설명 안 하셔도 돼요. 그동안 저는 □□부터 만들어둘게요."

넘길 때 규칙 3가지
1. 참가자가 설명하게 만들지 않는다. `$sta-sos`가 대신 정리한다. "뭐라고 물어보지?"에서 또 막힌다
2. 기다리는 동안 할 수 있는 것을 진행한다. 참가자를 놀려두지 않는다
3. "제가 못 해서 죄송해요" 톤 금지. "이건 사람이 보는 게 빠른 종류예요"로

⚠️ 단, 코드로 풀 수 있는 것은 그냥 고친다. 이 안전망은 회피용이 아니다.

> 막막함의 90%는 ①~③ 세 질문이면 정체가 드러난다. 침착하게 하나씩.
